# 🧬 Kiro Agent Core Directives & Playbook (2026)

Этот файл содержит фундаментальные правила, по которым агент должен действовать в данном проекте. Агент обязан **самостоятельно**, без явных пингов со стороны пользователя, применять инструменты, MCP-серверы и навыки (`skills`) в зависимости от контекста задачи.

---

## 🔹 БЛОК 1: УПРАВЛЕНИЕ АВТОНОМНЫМ ПОВЕДЕНИЕМ И MCP-СЕРВЕРАМИ

Вы, как Агент, имеете доступ к ряду MCP-серверов. Вы **обязаны** использовать их автономно:

1. **`Mem0 OpenMemory MCP` (Глубокая Память и Контекст)**
   * **Когда использовать:** При каждом значительном изменении архитектуры БД, логики работы приложения, создании нового микросервиса или принятии `ADR` (Architecture Decision Record). 
   * **Действие:** Если пользователь говорит "Я решил переписать систему авторизации на токены", вы *обязаны* вызвать инструмент добавления новой информации в Mem0.
   * **Сочетание с навыками (Skills):** `agent-memory-systems`, `agent-memory-mcp`. При старте сессии агент должен автоматически запрашивать у Mem0 дамп текущего архитектурного контекста.

2. **`DuckDuckGo` / `Brave Search MCP` (Ресерч и Внешний Контекст)**
   * **Когда использовать:** 
     - При встрече с неизвестной ошибкой в логах (стейк-трейсах), которая не гуглилась ранее.
     - При выборе библиотеки (выбор между A и B).
     - Когда пользователь просит "Проверь, как это сделано у конкурента X".
   * **Действие:** Перед тем как выдать ответ, отправьте запрос к MCP серверу поиска, получите актуальную техническую документацию (2026 года), и только после этого пишите код.

3. **`Puppeteer MCP` (UI/UX Аналитика)**
   * **Когда использовать:** Если задача касается Frontend/Дизайна и пользователь просит "Сделай красиво, как на таком-то сайте".
   * **Действие:** Используйте Puppeteer для получения DOM/Скриншотов референсного сайта, проанализируйте Tailwind/CSS классы, и примените их в проекте.

4. **`GitHub MCP Server` (Интеграция с репозиторием)**
   * **Когда использовать:** При завершении фичи или модуля.
   * **Действие:** Автоматическое прочтение открытых `Issue`, анализ `Pull Requests` на предмет уязвимостей, автоматическое написание CHANGELOG.

5. **`Sequential Thinking MCP` (Алгоритмическое планирование)**
   * **Когда использовать:** Перед написанием *любого* сложного алгоритмического кода (от 100 строк). Запрещено сразу писать код для сложной фичи.
   * **Действие:** Сначала сгенерируйте серию "размышлений" (Thinking process/Chain of Thought) через MCP, провалидируйте гипотезу на крайние случаи (edge cases) и граничные условия, и только потом генерируйте файлы.

## 🔹 БЛОК 2: ПРАВИЛА РАБОТЫ АГЕНТА (ЭФФЕКТИВНОСТЬ И КОНТЕКСТ)

1. **Экономия токенов:**
   * **Не используй `sequential-thinking` для базовых задач.** Запускай его ИСКЛЮЧИТЕЛЬНО для: сложных архитектурных решений, масштабного рефакторинга, тяжелых математических расчетов или запутанного поиска багов.
   * Для обычного написания кода, ответов или работы с файлами — применяй прямые инструменты сразу.

2. **Управление Контекстом:**
   * "Не тащи в инпут то, что можно спросить точечно".
   * Если нужно узнать схему БД, *запрещается* парсить все миграции через `list_dir` и `cat`. Используй Prisma MCP/Data Commons для SQL/Prisma запросов.
   * Всегда удаляйте старый мусор из чата.

3. **Структура документации проекта (КРИТИЧЕСКИ ВАЖНО):**
   * **Главный источник информации**: Папка `docs/` содержит всю документацию проекта с полной индексацией.
   * **Главные файлы индексации**:
     - `docs/config.json` - конфигурация разделов, навигация, настройки поиска
     - `docs/STRUCTURE.md` - полная карта структуры документации
     - `docs/NAVIGATION-MAP.md` - карта навигации по задачам
     - `docs/README.md` - обзор и точки входа
   * **Категории документации**:
     - `docs/api/` - API документация (OpenAPI, Swagger UI, примеры)
     - `docs/technical/` - техническая документация по модулям (AUTH, CLIENT, SERVER, DATABASE, GAMES, SOCIAL, STATS, SUBSCRIPTION, DESIGN, DEPLOY)
     - `docs/guides/` - руководства и инструкции
     - `docs/overview/` - обзоры, диаграммы, индексы
     - `docs/reports/` - отчеты о статусе и выполнении
     - `docs/viewers/` - HTML-просмотрщики для интерактивного просмотра
   * **Приоритет поиска информации**:
     1. Сначала проверь `docs/config.json` для понимания структуры разделов
     2. Используй `docs/NAVIGATION-MAP.md` для поиска нужного раздела по задаче
     3. Читай конкретные файлы из соответствующих категорий
     4. Используй DeepContext MCP для семантического поиска по документации
   * **Обновление документации**: При изменении архитектуры или добавлении функционала обязательно обновляй соответствующие файлы в `docs/`.

4. **Автономность и уверенность:**
   * **Работай автономно**: не спрашивай разрешения на запуск консольных команд, редактирование файлов или запуск тестов. Просто делай.
   * **Принимай решения сам**: изучай паттерны проекта и выбирай лучший вариант. Не пиши "Вам подходит такой вариант?". Задавай вопросы только при фатальных архитектурных рисках.

5. **Синергия Навыков (Skills):**
   * В вашем арсенале более 900+ встроенных навыков (в папке `global_skills`). При старте новой таски (команда `task_boundary`), агент обязан просканировать директорию и подгрузить 1-3 профильных скилла.
   * **Обязательно используй эту Матрицу Навыков (Core Skills Matrix) для частых задач:**
     * *Архитектура и Паттерны:* `ddd-strategic-design`, `ddd-tactical-patterns`, `design-patterns`, `software-architecture`, `microservices-architecture`
     * *Аналитика и Внешний контекст:* `competitor-alternatives`, `competitive-landscape`, `deep-research`, `product-strategy`
     * *Качество Кода и Оптимизация:* `code-review-guidelines`, `error-handling-patterns`, `performance-profiling`, `cost-optimization`, `context-optimization`
     * *Интеграции и Разработка (Backend/Frontend):* `react-best-practices`, `postgres-best-practices`, `api-design`, `mcp-builder`, `mcp-builder-ms`
     * *DevOps и Безопасность:* `security-audit`, `github-automation`, `ci-cd-pipelines`
     * *Тестирование:* `e2e-testing-patterns`, `unit-testing-best-practices`, `integration-testing`
     * *Автономность и Память:* `agent-memory-systems`, `agent-memory-mcp`, `task-breakdown`

## 🔹 БЛОК 3: ИНЖЕНЕРНЫЕ СТАНДАРТЫ (PARTY CHAOS / TRUE OR DO)

### 3.1. Качество кода и Локализация
- **Языки**: Для всего, что видит пользователь (тексты интерфейса, сообщения об ошибках, логи) используй **Русский язык**. 
- Для самого кода (переменные, функции, классы, ключи) используй **Английский**.

### 3.2. Архитектура и модульность
- **Переиспользуй готовое**: Прежде чем писать новые компоненты, проверь папку `server/src/game/` и `client/src/components/ui/`.
- Выноси логику в небольшие чистые модульные файлы.

### 3.3. Правила Socket.IO (КРИТИЧЕСКИ ВАЖНО)
- Формат событий **строго**: `{игра}:{сущность}:{действие}` (например, `alias:room:join`).
- После изменения данных на сервере **обязательно** вызывай рассылку синхронизации: `{game}:state:sync` для обновления клиентов.
- Состояние в оперативной памяти храни через `Map` или `Set`.
- Всегда обрабатывай ответные реакции (acknowledgements) через коллбэк `ack()`.

### 3.4. База данных (Prisma)
- Строго следуй уже описанной схеме в `schema.prisma`. Конвенции менять нельзя.
- Обязательно используй **Транзакции БД** для связанных операций.
- Оборачивай запросы в `try/catch`.

### 3.5. Frontend (UI/UX)
- Для анимаций **обязательно используй `Framer Motion`**.
- Вся верстка должна быть адаптивной под мобильные устройства (mobile-responsiveness).
- Каждое действие юзера должно визуально откликаться (лоадеры, тосты успехов/ошибок).

### 3.6. Тестирование
- Используй консоль для тестов сразу после написания кода.
- Клиент и сервер **должны работать в связке**.
- Удаляй за собой любые временные файлы (например, `tmp_rovodev_...`) после завершения проверки.

### 3.7. Работа с багами (Bug Resolution Workflow)
**При исправлении бага агент ОБЯЗАН:**
1. Прочитать баг из `docs/plan/bugs.json`
2. Исправить код
3. Написать краткий отчёт о решении (что исправлено, где, как)
4. Обновить баг через PATCH `/api/bugs/:id` с полями:
   - `status: "resolved"`
   - `assignee: "Kiro Agent"`
   - `resolution: "[отчёт]"`
5. Отчёт должен содержать: файл, строку, что изменено, как это решает проблему

**Формат отчёта:**
```
Исправлена функция X() в file.js (строка Y). Добавлен/Изменён Z. Теперь [результат].
```

**Пример:**
```
Исправлена функция shuffleTeams() в server/src/game/codenames.js (строка ~1307). 
Добавлен фильтр p.team !== TEAMS.SPECTATOR при выборке активных игроков. 
Теперь shuffle распределяет только игроков в командах RED/BLUE, спектаторы 
остаются наблюдателями и не попадают в игру.
```
