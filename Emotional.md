# План: «Эмоциональный интеллект»

## ЦЕЛЬ
Реализовать новую игру с полной игровой логикой, состояниями раундов, подсчётом очков и UI-поведением.

### Ключевая идея
Актёрская передача эмоции + блеф.
Игра намеренно **НЕ** поощряет угадывание, а поощряет убедительность и манипуляцию.

### ВАЖНО
- Не менять механику и баланс для удобства или логичности.
- Все спорные решения ниже — осознанные.

## ОСНОВНАЯ МЕХАНИКА ИГРЫ

### Ход раунда
1) Определяется ведущий раунда.

#### Порядок хода (ведущего)
- ход идёт **по очереди**
- **хост ходит первым** (создал комнату; первый в списке)
- дальше — по **порядку присоединения** игроков

2) Ведущий:
- тянет **секретную эмоцию** из колоды
- никто, кроме него, её **не видит**

3) Всем игрокам показывается **один общий текст** из `words.txt`.

4) Ведущий зачитывает текст, **отыгрывая свою секретную эмоцию**.

### Выкладка карт
Все игроки, включая ведущего:
- **одновременно**
- **вслепую**
- выкладывают **одну** карту эмоции из своей руки

Пояснение «вслепую»:
- игроки **видят свои карты**
- «вслепую» означает, что выложенные карты **изначально перевёрнуты**, и их нужно **открывать позже хосту**

#### Таймер этапа выкладки
- запускается таймер **1 минута**
- если игрок не выложил карту до конца таймера:
  - он **пропускает весь раунд**
  - **не участвует** в голосовании
  - **не получает** очки
  - его статус **явно отображается** в UI

- как только все активные игроки выложили карты — таймер **останавливается досрочно**

#### Появление карт на столе
После завершения этапа выкладки:
- все выложенные карты появляются **одновременно** на столе
- карты **анонимны** — нельзя определить владельца
- количество карт на столе = количество **активных** игроков

### Голосование
Игроки голосуют за **одну** карту, которая, по их мнению, **лучше всего соответствует** отыгранной эмоции.

Разрешено:
- голосовать за **свою** карту
- голосовать за карту **ведущего**

При этом:
- игроки **не знают**, какая карта принадлежит ведущему

### ПОДСЧЁТ ОЧКОВ (КРИТИЧЕСКИ ВАЖНО)

#### Основное правило
Очки получает **только** владелец карты, набравшей **максимум голосов**.

#### Сценарии

**1) Побеждает карта ведущего (настоящая эмоция)**
- ведущий получает **+2** очка
- все остальные игроки получают **0** очков (даже если голосовали «правильно»)

**2) Побеждает карта НЕ ведущего**
- владелец этой карты получает **+1** очко
- ведущий получает **0** очков
- остальные игроки получают **0** очков, независимо от их выбора

**3) Ничья по максимальному количеству голосов**
Каждый владелец карты-победителя получает очки:
- если среди победителей есть ведущий — ведущий получает **+2**
- остальные победители получают **+1**

Очки **суммируются независимо**.

#### ВАЖНОЕ ОГРАНИЧЕНИЕ
Игроки, которые угадали эмоцию, **НЕ получают очки**, если **их карта не победила**.
Это намеренное решение. **Не изменять.**

### КОНЕЦ РАУНДА
После подсчёта очков:
- всем игрокам показывается:
  - настоящая эмоция ведущего
  - кто какие очки получил
- ход **немедленно** передаётся следующему игроку

### КОНЕЦ ИГРЫ
- целевое количество очков **настраивается** (например, 15 или 30)
- как только любой игрок достигает цели:
  - игра **мгновенно** завершается
  - **без доигрывания раунда**
  - объявляется победитель

### Игроки и карты
- Каждый игрок всегда имеет **ровно 8 карт эмоций**.
- Существует **одна общая колода эмоций**.

### Правила добора
После каждого раунда:
- игрок, выложивший карту, автоматически добирает **1** карту из колоды
- если колода пуста — добор не происходит

Ограничения:
- перемешивание, ресет или автогенерация эмоций **запрещены**

### Файлы контента
- `server/data/emotional/emotions.txt` — список эмоций
- `server/data/emotional/words.txt` — тексты для зачитывания

#### Формат `emotions.txt` и `words.txt`
- кодировка: **UTF-8**
- **одна запись на строку**
- **без пустых строк**
- без нумерации/маркеров (только текст)

Пример `emotions.txt`:
```text
Радость
Злость
Тревога
```

Пример `words.txt`:
```text
Я зашёл в комнату и увидел то, чего не ожидал.
Сегодня мой самый странный день.
```

## Как максимально правильно добавить новую игру в PartyChaos (пошагово)

Ниже — эталонный чек-лист/процесс, ориентированный на текущую архитектуру проекта (как сделаны **Alias** и **Codenames**). Его цель — добавлять игру так, чтобы:
- **не ломать существующие игры**,
- **не плодить отдельные архитектуры**,
- сразу заложить основу под полноценную логику, синхронизацию состояния и UI.

### 0) Перед стартом: определить контракт игры
1) Зафиксировать:
   - название игры (UI) и `gameKey` (технический ключ, латиница, lowercase), для этой игры: `emotional`
   - набор Socket.IO событий по конвенции `{game}:{entity}:{action}`
   - минимальный state комнаты (что сервер хранит и что клиент рисует)
2) Сразу решить, что является «истиной»:
   - **сервер** — источник правды (room state + тайминги)
   - **клиент** — только отображение и отправка действий

### 1) Данные/контент (если нужны)
1) Добавить папку данных игры в `server/data/{gameKey}/`.
2) Определить формат файлов (обычно: UTF‑8, одна запись на строку, без пустых строк).
3) На сервере сделать загрузчик (если нужно) или использовать существующие утилиты чтения.

Для «Эмоционального интеллекта» уже зарезервировано:
- `server/data/emotional/emotions.txt`
- `server/data/emotional/words.txt`

### 2) Сервер: каркас игровой логики
Цель этапа: игра должна уметь **создавать комнату**, **пускать в неё игроков**, **держать состояние** и **рассылать sync**.

1) Создать модуль игры в `server/src/game/emotional.js` (или несколько файлов рядом, если логики много).
2) Внутри модуля:
   - определить структуру room state (минимальную, затем расширять)
   - создать функции-хелперы (валидации, генерация initial state, применение actions)
3) Важно: не смешивать Socket.IO обработчики и «чистую» логику. Паттерн проекта —
   - Socket.IO handler: принимает payload → вызывает функции game module → обновляет state → эмитит sync

### 3) Сервер: Socket.IO события (index.js)
Цель: добавить события игры рядом с существующими `alias:*` / `codenames:*`.

1) В `server/src/index.js` зарегистрировать события:
   - `emotional:room:create` (создание комнаты)
   - `emotional:room:join` (вход по коду)
   - `emotional:state:sync` (обычно это emit от сервера; клиент слушает)

2) Каждое событие:
   - обязано поддерживать `ack` (callback) и возвращать `{ ok: true, ... }` или `{ ok: false, error: "..." }`
   - после любых изменений state — делать `io.to(roomCode).emit("emotional:state:sync", state)`

3) Хранение состояния:
   - если в проекте уже есть общий механизм комнат — использовать его
   - если у каждой игры свой in-memory state — следовать существующим структурам (как в alias/codenames)

### 4) Клиент: страница игры и роутинг
Цель: ссылка на игру открывает экран входа, дальше — экран комнаты.

1) Добавить страницу `client/src/pages/EmotionalPage.jsx` (+ `.css` при необходимости) по образцу `AliasPage` / `CodenamesPage`.
2) Подключить страницу в роутинг:
   - посмотреть, где подключаются страницы: `client/src/pages/index.js`, `client/src/RoutesRoot.jsx`, `client/src/App.jsx`
   - добавить новый route (как сделано для Alias/Codenames)
3) В список игр (страница `GamesPage`) добавить карточку/плитку новой игры (если список задан явно).

### 5) Клиент: компоненты игры
Минимальный набор для первой итерации (чтобы навигация и базовая сессия работали):
1) `client/src/components/emotional/EmotionalJoinScreen.jsx`
   - UI «Создать комнату / Войти по коду / Профиль / Правила»
   - логика как в Alias/Codenames
2) `client/src/components/emotional/EmotionalRulesModal.jsx`
   - модалка правил (можно из текста этого документа)
3) `client/src/components/emotional/EmotionalRoomScreen.jsx`
   - «каркас комнаты» (хедер как у Alias/Codenames + заглушка контента)

Рекомендация по структуре:
- завести папку `client/src/components/emotional/` (как `alias/` и `codenames/`)
- переиспользовать `client/src/components/ui/*` (кнопки, модалки, баннеры)

### 6) Клиент: Socket.IO интеграция
1) В `EmotionalPage` (или `EmotionalRoomScreen`, как сделано в других играх) подключить:
   - emit `emotional:room:create`
   - emit `emotional:room:join`
   - on `emotional:state:sync` → обновлять локальный state
2) Важно:
   - чистить listeners в `useEffect` cleanup
   - не хранить «серверные» данные в нескольких местах

### 7) Общий UX-стандарт (не пропускать)
1) Хедер комнаты: профиль / код комнаты (копирование ссылки) / кнопки `?`, settings, leave.
2) Все ошибки — на русском и человеко-понятно:
   - «Комната не найдена», «Неверный код», «Нет прав» и т.п.
3) Все действия — с визуальным фидбеком (loading/disabled).

### 8) Тестирование (минимум перед “готово”)
1) Поднять server + client.
2) Проверить:
   - открывается страница игры
   - создаётся комната
   - второй клиент заходит по коду
   - state sync приходит обоим
   - выход/перезаход не ломает комнату

### 9) Как мы будем работать дальше (процесс)
- Ты даёшь задачи **по очереди**.
- Я реализую задачу и **обновляю TODO-лист ниже** (ставлю галочки, добавляю новые подзадачи при необходимости).

- масштабирование/адаптивность должны быть оптимальны:
  - для компьютерной версии
  - для мобильной версии
  - для узких мониторов
  - для малой высоты экрана
- анимации:
  - переворота карт (**flip**)
  - появления карт на столе
- клик по карте:
  - подсветка
  - чёткое состояние «выбрано»
- таймер:
  - визуально заметный

- явное отображение:
